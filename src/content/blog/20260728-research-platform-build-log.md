## 一、今天建立網站的主要目標

這次的目標不是只做一個單純的個人首頁，而是慢慢把網站整理成一個可以長期使用的研究管理中心。

一開始網站主要是用來記錄 Blog 文章，後來逐步加入分類、標籤、任務、週報、Dashboard、登入系統、研究筆記，以及文獻搜尋與文獻庫。整體方向是希望把平常研究中分散在對話、檔案、筆記、任務清單和文獻搜尋中的內容，集中整理到同一個平台上。

目前這個網站的定位可以先理解成：

- 記錄每日學習與研究過程
- 管理任務與週報
- 收藏想繼續閱讀的論文
- 將文獻搜尋、分析與筆記保存成自己的研究資料庫
- 讓之後回顧研究進度時，有一個清楚的入口

## 二、一路上可能遇到的問題

### 1. 靜態網站和資料庫功能的界線

Astro 原本很適合做靜態網站，例如 Blog、分類頁、標籤頁都可以在 build 時產生。

但是任務、週報、登入、研究筆記和文獻庫這些功能需要儲存資料，所以不能只靠 Markdown 或 JSON 檔案。這時候就需要接 Cloudflare Workers 和 D1 資料庫。

這裡的挑戰是：不能一次把所有頁面都改成資料庫版，否則很容易破壞原本已經可以運作的 Blog。因此採取的方式是逐步加入 D1 foundation，讓需要動態資料的頁面使用 server route，原本的靜態內容則繼續保留。

### 2. Cloudflare secret 與登入設定

登入系統不能把帳號、密碼、token 寫進 GitHub repository。

因此本人帳號、密碼、session secret、API token 都需要放在 Cloudflare Secret 裡。本機測試可以使用 `.dev.vars`，但這個檔案必須被 `.gitignore` 忽略。

這個過程容易遇到的問題是：

- Cloudflare secret 還沒有設定，登入 API 會無法使用
- 本機和正式環境的 secret 不一致
- 瀏覽器可能記住帳密，需要關掉表單自動填入
- GitHub 或 Cloudflare CLI 需要重新登入

這些問題不一定是程式寫錯，而是部署環境和權限設定還沒有完全接好。

### 3. D1 schema 要能逐步擴充

任務、週報、研究筆記、文獻庫都需要不同資料表。

一開始如果資料表設計太複雜，後面會很難維護；但如果設計太簡單，又沒辦法保存標籤、分析結果和閱讀狀態。

目前採用的方式是：

- 任務放在 `tasks` 和 `task_tags`
- 週報放在 `weekly_reports` 與相關 section / tag / category 表
- 研究筆記放在 `journal_entries`
- 文獻庫放在 `papers`
- 文獻分析結果放在 `paper_analyses`

這樣可以先滿足現在的需求，也保留之後擴充的空間。

### 4. 文獻分析不要直接綁外部 AI API

老師提醒文獻總結系統應該方便自己使用，不一定要把文件上傳到 API 分析。

所以目前文獻分析採用瀏覽器本地端規則式整理：使用者可以貼上摘要或全文，網站在前端產生幾種分析框架，例如五分鐘速覽、方法復現、審稿人視角和讀書會報告。

這樣的好處是：

- 不需要把 PDF 或全文送到外部 AI
- 可以快速產生閱讀大綱
- 適合先做研究紀錄和個人整理
- 之後若真的要接 AI，也可以建立在這個流程上

目前的限制是：它還不是完整的 AI 理解系統，所以對複雜論文的摘要品質仍需要人工檢查。

### 5. GitHub、build 和部署流程

每次修改後都需要確認：

- `npm run build` 是否成功
- GitHub main 是否是最新版
- Cloudflare 是否成功部署
- D1 schema 是否已經套用到本機與遠端
- 是否不小心提交了 `.dev.vars`、token 或密碼

這些流程看起來繁瑣，但對正式網站很重要，因為只要其中一個環節沒處理好，網站就可能在本機能跑、正式環境卻不能用。

## 三、我和 AI 協作的溝通方式

這次和 AI 協作時，比較有效的方式是把任務拆成明確的功能需求，而不是只說「幫我做一個網站」。

例如每次修改都會先說明：

- 目前網站已經有什麼
- 這次只要新增什麼
- 哪些檔案可以修改
- 哪些功能不要動
- 要不要建立分支或 PR
- 要執行哪些測試
- 完成後要回報哪些項目

這種溝通方式讓 AI 比較不會亂改無關功能，也比較容易維持網站原本的風格。

比較重要的經驗是：當需求變大時，最好先把它拆成階段。例如先做分類與標籤，再做任務與週報，再做 D1，再做登入，再做文獻庫。每一步完成後再繼續往下，比一次把所有東西塞進去穩定很多。

## 四、目前已新增的功能

### 1. Blog 分類與標籤系統

Blog 文章已經有 `category`、`tags` 和 `draft` 欄位。

目前已完成：

- `/categories/` 分類總覽頁
- `/categories/[category]/` 單一分類文章頁
- `/tags/` 標籤總覽頁
- `/tags/[tag]/` 單一標籤文章頁
- Blog 列表中的分類與標籤可點擊
- Blog 頁面上方有所有分類、所有標籤入口
- Blog 頁面可以依分類快速篩選
- 搜尋功能可以和分類篩選一起使用

### 2. 任務系統與週報系統

網站目前有 `/tasks` 和 `/weekly`。

任務系統可以整理每日任務與每週任務，並用狀態和優先順序分類。週報系統可以整理完成事項、進度、問題、解法、未完成項目和下一週目標。

後來又加入 D1 版本，讓任務不只存在 JSON，也可以透過受保護 API 新增、修改、完成或清空。

### 3. 研究儀表板

`/dashboard` 是目前網站的研究管理中心。

它整合了：

- 任務狀態摘要
- 進行中任務
- 高優先任務
- 最新週報
- 最新 Blog 文章
- 最新研究筆記
- 最新收藏文獻
- 快速入口

這個頁面讓網站比較像一個研究工作台，而不只是文章列表。

### 4. 登入與權限

網站目前有本人登入與訪客身分。

本人登入後可以進入管理頁，新增任務、撰寫研究筆記、儲存文獻和編輯文獻筆記。訪客可以瀏覽公開頁面，但不能寫入資料。

登入資訊使用 Cloudflare Secret 管理，沒有寫入 GitHub repository。

### 5. 研究筆記與日誌撰寫

目前已有 `/journal` 和 `/journal/admin/`。

`/journal` 用來公開顯示已發布的研究筆記，`/journal/admin/` 是本人登入後使用的撰寫頁。

目前功能包含：

- 建立草稿
- 發布研究筆記
- 編輯標題、摘要、分類、標籤與日期
- 使用富文字區塊撰寫內容
- 支援貼入小型圖片

這個功能比較適合用來記錄每日研究想法、實驗觀察、計算流程與臨時筆記。

### 6. 文獻搜尋與文獻庫

`/literature` 目前是文獻搜尋與本地分析入口。

已完成的功能包含：

- OpenAlex 文獻搜尋
- 依關聯度、引用數、年份排序
- 篩選近 5 年或近 10 年文獻
- 只顯示 Open Access 文獻
- 快速搜尋常用研究主題，例如 high entropy alloy、DFT、catalysis
- 開啟 Google Scholar、Semantic Scholar、Crossref 交叉搜尋
- 將搜尋結果帶入分析器
- 將搜尋結果儲存到文獻庫
- 將本地分析結果儲存到文獻庫

`/papers` 是我的文獻庫。

目前可以保存：

- 論文標題
- 作者
- 年份
- 期刊
- DOI 或來源連結
- 摘要
- 引用數
- Open Access 狀態
- 閱讀狀態
- 標籤
- 個人筆記
- 本地分析結果

這個設計比較符合老師說的方向：先搜尋文獻，接著在本地端分析與整理，再存成自己的文獻資料庫。

## 五、目前網站的使用流程

目前可以先照這個流程使用：

1. 到 `/literature` 搜尋研究主題
2. 用 OpenAlex 或外部平台交叉確認文獻
3. 找到想之後看的論文後，先存到 `/papers`
4. 貼上摘要或全文，產生本地分析
5. 把分析結果存回同一篇文獻
6. 到 `/journal/admin/` 撰寫當天研究日誌
7. 如果有具體待辦，新增到 `/tasks`
8. 到 `/weekly` 查看自動週報大綱
9. 從 `/dashboard` 回顧整體研究狀態

## 六、下一步可以改進的地方

目前網站已經有研究管理平台的雛形，但還有幾個地方可以繼續改：

- 文獻分析目前是規則式整理，之後可以再研究是否接本地模型或更完整的 AI 流程
- PDF 文字抽取仍有限制，有些掃描 PDF 或壓縮 PDF 需要手動貼文字
- 圖片目前以小型 data URL 放在研究筆記中，大量圖片之後適合改用 Cloudflare R2
- 文獻庫可以再加入期刊定期掃描功能
- 週報可以再加入「一鍵保存本週週報」功能
- 研究筆記和 Blog 文章之間可以再建立更清楚的關係

## 七、今天的整理心得

今天最大的收穫是：網站不一定要一次做成很完整的系統，但每一步都要能真的接到自己的研究流程。

如果只做漂亮頁面，之後很快就不會用了；但如果能把搜尋文獻、閱讀、筆記、任務和週報串在一起，網站就會慢慢變成真正的研究工具。

這次也發現和 AI 協作時，最重要的是清楚描述「目前狀態」和「這次不要做什麼」。只要範圍清楚，AI 比較能幫忙把一個大系統拆成可以逐步完成的小功能。

接下來可以開始實際把每天的研究過程寫進去。只要有真實內容累積，之後要調整頁面、資料欄位和功能方向時，就會更知道自己需要的是什麼。
